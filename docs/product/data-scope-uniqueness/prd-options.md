# 数据域冲突处理方案比较

## A. 只靠前端检查

优点：改动少，填写时反馈快。

缺点：调用 API、旧页面、并发操作或 Rust 运行时都可以绕过；不能作为隔离边界。

结论：不采用。

## B. Node 与 Rust 后端强制唯一，前端预检（采用）

账号开通与密码重置接口统一比较目标 `dataScope` 和其他已配置登录账号。冲突返回 `409` 与可恢复说明；界面仅作预检，保留服务端错误原文。

优点：两个运行时的隔离语义一致，能覆盖 API 调用和并发校验；owner 填写时无需等到提交后才知道问题。

代价：users file 中的历史重复配置需要 owner 人工明确处理，不能静默猜测数据归属。

## C. 把 dataScope 改成服务端随机 ID

优点：表层上不易误填重复。

缺点：需要迁移所有既有 runtime 数据、用户配置和排障工具，超过本轮风险可控范围。

结论：待明确多租户和迁移方案后再评估。

# 评审与裁决

## 产品视角

当前产品是邀请制个人求职教练，不支持组织共享工作区。一个可登录账号对应一个私有数据域，因此重复 `dataScope` 不是协作功能，而是越权风险。采用后端强制唯一的方案 B。

## 技术视角

Node runtime JSON 与 Rust SQLite 都以 `dataScope` 作为服务端隔离键。只修 React 本地快照不能阻止 owner 配置出两个相同 scope 的账号，必须在两套 users file 开通实现中同步校验。

## UI/UX 视角

数据域输入保留默认同登录名的认知模型。前端在 owner 已读取到的账号清单中给出即时冲突信息，保存失败仍显示后端的明确恢复动作，避免把错误做成无上下文的通用失败。

## QA 视角

覆盖 Node/Rust：创建 Mia 后尝试创建另一账号并复用 `mia` 数据域，断言 `409`、账号未写入、邀请未写入、Mia 的原数据仍可登录。前端覆盖同登录名可编辑、不同登录名冲突与空数据域默认值。

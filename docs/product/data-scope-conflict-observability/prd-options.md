# 历史数据域冲突方案比较

## A. 不处理历史配置

优点：零改动。

缺点：重复数据域继续隐藏，owner 无法判断新用户为什么看到了旧数据。

结论：不采用。

## B. 只在前端根据当前台账推断

优点：实现简单。

缺点：邀请记录不等于可登录账号，且可绕过 users file 的真实状态；Node 与 Rust 会不一致。

结论：不采用。

## C. 后端检测并由 owner 显式处理（采用）

优点：以 users file 的可登录账号为事实源，Node/Rust 合同一致；不改变历史数据。

代价：owner 仍要确认每个账号应保留的数据域和密码重置时机。

## D. 自动为每个账号生成新数据域并迁移

优点：表面上可一次性消除重复。

缺点：无法可靠判断历史 runtime 属于哪个账号，可能造成数据丢失或错误归属。

结论：超出本轮安全边界。

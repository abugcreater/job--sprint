# 方案比较

## 方案 A：监听 `popstate` 后回滚历史

发现浏览器后退后再调用 `history.go(1)` 或重新写入 hash，弹窗确认后再返回。

优点：不需要调整路由架构。

缺点：浏览器已经发生导航，回滚会造成额外历史项、闪烁、前进/后退语义不稳定；与既有 Android 返回策略也容易重复处理。

结论：拒绝。

## 方案 B：迁移到 Hash 数据路由并使用 `useBlocker`

保持现有 `#/...` URL，使用 `createHashRouter` + `RouterProvider` 建立数据路由。由官方 `useBlocker` 在导航提交前暂停历史 `POP` 和页面内路由导航，确认后调用 `proceed()`，继续编辑调用 `reset()`。

优点：不伪造历史；`POP`、链接和代码导航走同一机制；确认后的导航只执行一次。

代价：需要把声明式 `HashRouter` 路由表改为对象路由，并将守卫测试迁移到数据路由测试容器。

结论：推荐。

## 方案 C：自动保存草稿后允许返回

把各页面草稿写入 localStorage 或服务端，允许浏览器直接后退。

优点：理论上降低确认频率。

缺点：需统一草稿协议、清理时机、账号隔离、加密和恢复 UX；会把本次导航问题扩大为数据生命周期项目。

结论：不纳入本轮。

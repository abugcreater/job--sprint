# Android 系统返回未保存内容保护方案比较

日期：2026-08-02

| 方案 | 做法 | 优点 | 不选或风险 |
|---|---|---|---|
| A：重复写入浏览器历史 | 脏草稿时插入历史记录，再监听回退并反向跳转 | 不需要原生桥 | 容易形成返回循环，破坏历史语义，与已知问题的明确禁令冲突。 |
| B：原生-网页单次协商 | Android 先派发可取消事件；脏草稿由 React 显示确认，确认后调用受限桥完成一次真实返回 | 保留系统返回语义，复用现有确认体验，范围小且可测 | 需要新增极小的 WebView JS bridge，并限定其能力。 |
| C：全量自动保存与恢复 | 每次输入写本地或服务端草稿，返回时允许直接离开 | 可覆盖强杀恢复 | 数据模型、隐私边界、恢复冲突和跨端规则都未定义，超出每日任务。 |

## 裁决

采用方案 B。系统返回由原生发起，但是否拦截由当前 React dirty 回调决定；用户明确确认后才执行 `goBack()` 或退出。桥不接触账号、Cookie、远端 URL、文件、录音或任何业务数据。
